# 供应商独立请求预算

在供应商添加或编辑表单中展开 **本地代理请求预算**。Claude Code、Codex、Gemini、Grok Build 和 Claude Desktop 的本地代理路径使用这些设置。直接连接上游、个人 Node shim、模型目录和连通性探测不使用它们；Claude Desktop 官方直连不显示此入口。

所有字段默认留空，沿用应用现有策略。填写 **1–3600 的整数秒** 后仅覆盖该供应商；清空即可恢复继承。修改对保存后的新请求生效，不改变已运行请求。显式供应商预算在故障转移关闭时也生效；未配置的旧供应商保持原来的应用超时开关语义。

| 字段         | 生效阶段                                                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 首字节预算   | 流式请求的一次准备和发送，直至上游响应头、首段数据与既有输出前检查完成。超时可按既有故障转移规则选择备用，同一家不会因此额外自动重发。 |
| 流空闲预算   | 已交付流在读取下段数据时，允许的最长无数据间隔。使用实际成功供应商的设置；不限制持续有数据的完整流长。                                 |
| 非流式预算   | 一次准备和发送至完整响应体读取，避免响应头已到但正文一直不结束。                                                                       |
| 输出前总预算 | 从本地代理开始首次转发计时，包含发送、429 冷却、恢复许可排队、同家重试和修正重试。切换备用不重新计时；备用显式总预算只能收紧原期限。   |

总预算耗尽后返回 HTTP 504，诊断显示“输出前总预算已耗尽”。请求结束会释放等待记录、恢复许可与连接计数。该期限停止作用于已交付的流，流空闲预算继续独立生效；它不能控制客户端自己的超时，也不是服务器端任务的撤销承诺。取消或停止代理会终止本地等待及后续发送，上游已经接受的任务可能仍由上游执行。

应用原有重试次数、429 单次等待上限和恢复许可继续生效。总预算较短时请求可能在冷却期间结束，但不会缩短共享 `Retry-After` 后再提前发送。默认不增加重试次数、不更换用户候选顺序，原生状态型 Codex 请求的一次发送保护、文本/推理/工具活动后的禁止重放和默认关闭的加密历史兼容均保留。

## 诊断与存储

在 **设置 → 路由 → 请求诊断** 查看请求时间线。发送步骤可附带当时的输出前预算剩余毫秒；这是步骤发生时的快照，不是持续倒计时。预算耗尽使用固定错误分类 `recoveryBudget`，终态为 `timedOut`。复制脱敏摘要会包含这些数值，不包含新的请求正文、密钥、网址、会话标识或错误原文。原有数量及保留时间限制不变，见[请求诊断](REQUEST-DIAGNOSTICS.md)。

供应商元数据新增可选 `meta.requestBudget`，只存本地代理设置，不写入客户端 live 配置或发给上游。没有新数据库表或 schema 迁移；旧数据缺少字段时继续正常读取。界面和保存入口拒绝 0、负数、小数及超大值；通过 SQL 导入绕过保存校验时，运行时忽略 0、把正数上限限制为 3600 秒，不接受“0=禁用”覆盖。

## 验证范围

本轮仅使用回环模拟上游、合成历史和虚构密钥，不读取个人客户端密钥或会话，不调用付费 API。[源码 CI `45158165294`](https://github.com/yunhanhai/yunswitch/actions/runs/45158165294)与 [Windows 新包验收 `45158157193`](https://github.com/yunhanhai/yunswitch/actions/runs/45158157193)均通过。

本机相关前端 6 文件、54 项通过，预算专项 Rust 13 项通过（与代理回归有重叠），类型/格式和 renderer 构建通过，界面静态检查无发现；代理相关回归复跑 1587 项通过。首次回归的一个既有 Codex 429 场景遇 Windows 本机连接中止，单独复验和整组复跑均通过。标准严格 Clippy 已通过；额外尝试 `--all-targets` 时在未改动的 `routing_groups.rs` 与 `deeplink/parser.rs` 发现两项既有测试代码告警，不将其表述为全部 target 的严格检查通过。最终 PR CI 覆盖前端 147 文件 / 1114 项、三平台后端与 Windows+WSL2，均成功。

Windows 真实包 **122 项检查通过，0 项失败**，便携与 `.7` 升级后的 MSI 均验证实际预算表单读取/编辑/保存、故障转移关闭时覆盖生效、总预算停止同家退避、并发冷却与许可排队回收、输出后空闲失败不重放和取消后无额外发送。产品与验收源码为 `f24f8c9ddec9b83007141027e4722e99e6726442`；回读 MSI SHA-256 `9a22d7d80eb427cead4525e5d394577476f62648e3374be9b08e42bab2d4a903`，便携 ZIP `c28997484dd820a6d432039186970632722b0efdeb262bf25f572c8ea2ed19a7`。这是沿用 `.8` 版本号的 build-only 产物，未替换公开 Release。

初次包 `c7a12fb9` 的验收先遇到测试通过 IPC 添加供应商后界面缓存未刷新；脚本刷新并使用键盘编辑后，又发现真实编辑器异步载入 live 配置会重置预算草稿。现已按供应商身份及预算值独立初始化，并新增“迟到实时配置不覆盖草稿”回归，再重新构建上述最终包完成验收。旧包和失败复验不作为最终通过证据。

测试覆盖不同发送路径、响应头/正文超时、同家退避、备用不延长期限、并发冷却/排队、取消清理、输出超过总期限后仍可完成、输出后流空闲失败不重放、状态型 Codex 一次发送，以及诊断安全分类。实际供应商、所有协议组合、长会话和 macOS/Linux 安装包仍需分别验证。

设计参考[固定版本的 shim 对照](SHIM-OPTIMIZATION-REVIEW.md)，预算和取消管理按 YunSwitch 现有 Rust 代理实现，没有复制 shim 的 Node 重试循环。此前指出的输出后协议安全终态、原生稳定缓存键补齐仍属于后续独立工作。
